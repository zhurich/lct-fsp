# ФСП Карьера — контекст проекта

Хакатон, спец. трек ФСП. ТЗ: `docs/tz.txt`. Финальная сдача — 11.10.2026, разработчик один, поэтому
приоритет — скорость и два главных критерия, а не объём CRUD.

## Критерии (веса)

Механика подбора и выхода на контакт — 35%, тестирование и категоризация с валидацией — 25%, интерфейс — 10%,
питч — 10%, техническая проработка — 7%, доп. функционал — 7%, полнота и документация — 6%.

## Принятые решения

- Стек: FastAPI + SQLAlchemy (sync) + PostgreSQL, React + TS + Mantine 8 + TanStack Query, Docker Compose.
- Авторизация своя: почта + пароль (argon2), подтверждение почты, JWT в httpOnly-cookie. Keycloak не
  поднимаем. Вход через ФСП ID имитируется (`fsp/idp.py`): контракт `FspIdProvider` + мок по схеме
  Authorization Code — страница провайдера `/fsp-id`, возврат на `/fsp-callback` с одноразовым кодом и
  подписанным state. Мок принимает любую почту с паролем `fsp-demo`, ID участника выводит из почты
  (семизначный, чтобы не пересекаться с шестизначными ID сида). Первый вход создаёт кандидата без пароля;
  по совпадению почты учётные записи не объединяются (409). Привязка в настройках — только через этот вход,
  ручного ввода ID нет.
- Итоги Q&A с организаторами (06.10.2026) учтены; регрессионные тесты — `tests/test_qa_session.py`.
  Зарплаты везде подписаны «до вычета НДФЛ» (`SALARY_NOTE` в `frontend/src/reference.ts`).
- Демо-режим стенда (`DEMO_MODE=true`): регистрация без подтверждения почты и
  `POST /candidate/assessment/reset` — сброс своих попыток и категории, чтобы жюри могло пройти тест
  несколько раз. По умолчанию выключен; сроки пересдачи при этом не меняются.
- Локально Docker и PostgreSQL нет: разработка на SQLite, поэтому типы колонок только переносимые (JSON, без
  pgvector и специфики Postgres). Compose-сборка локально не проверялась.
- Доступа к LLM нет: всё, что могло бы использовать LLM (разбор резюме, разбор потребности работодателя),
  делается правилами и словарями, с точкой расширения под модель.
- Движок теста (`assessment/`): `bank.py` — 28 общих параметризованных заданий (7 шаблонов × 4 уровня),
  `bank_spec.py` — по 8 ситуационных вопросов на специализацию, `bank_glossary.py` — задания на термины
  (2 глоссария × 8 пар на специализацию), `adaptive.py` — IRT 3PL без зависимостей от БД. Тест — от 12 до
  18 заданий по одному (`MIN_LENGTH`, `MAX_LENGTH`), каждое третье профильное: задания подбираются по
  информации в точке границы заявленного грейда, тест заканчивается при уверенности 90% в решении
  (`is_finished`). Шкала θ: граница грейда i = i − 2, балл = 50 + 15·θ. Параметры a и b назначены экспертно,
  по реальным ответам не калибровались. Политика выбрана симуляцией: против фиксированных 15 заданий «под
  текущую оценку» категория точнее (75% против 72%), но балл грубее (надёжность 0,65 против 0,74) и зависит
  от грейда теста. Завершённая попытка — та, у которой у последнего задания есть ответ (`is_complete`).
- Мониторинг дрейфа (`assessment/drift.py`, таблица `item_flags`): после каждого завершённого теста профильные
  задания специализации сверяются с ожидаемой решаемостью; уровень кандидата для сверки — только по общим
  (генерируемым) заданиям попытки. Превышение больше 15 п.п. и 2,5 σ при 30+ ответах снимает задание с
  выдачи (`adaptive.position_pool` подставляет общие). Флаг снимается только вручную — удалением строки.
- Движок подбора (`matching/`): `parser.py` — разбор текста потребности правилами (точка расширения под LLM —
  функция `parse_need`), `ranking.py` — оценка без зависимостей от БД: 85% соответствие (грейд 0,4 / стек 0,45 /
  формат 0,15) + до 15% сила профиля (тест 0,6 / ФСП 0,25 / свежесть 0,15). Сила профиля только упорядочивает
  равных по соответствию: её вес ограничен 90% «цены» одного требования запроса (`strength_share`), поэтому
  недостающую технологию она не перевешивает; при доле 40% валидация показала худший топ. Смежный грейд входит в подборку с
  половинным весом, дальше смежного — нет. Близкая технология (`skills._RELATED_GROUPS`: MySQL ↔ PostgreSQL,
  Kafka ↔ RabbitMQ) закрывает требование наполовину и в `matched_stack` не входит. Объяснение — список
  `Reason(kind, text)`: `plus` / `minus` / `info`; место кандидата по баллу среди своей категории
  (`test_percentile`) считает роутер при пяти и более кандидатах. На фронтенде минус рисуется тёмным, не красным.
- Неподтверждённый грейд: кандидат без категории с непройденным тестом не скрывается, а идёт отдельным
  списком после подборки (`describe_unverified`, `CandidateCard.verified = false`, `MatchesOut.unverified`):
  без оценки, заявленный грейд — из последней непройденной попытки, отбор по специализации и смежности
  грейда тот же. Счётчики категорий и `total` — только по подтверждённым. Пригласить такого можно;
  не сдававший тест в выдачу не попадает.
- Профиль (`candidates/`): `resume.py` — разбор PDF-резюме правилами (pypdf), файл не хранится, результат —
  черновик формы; `pdf.py` — PDF-профиль (fpdf2, шрифт DejaVu в Docker / Arial локально). Приватность —
  `hidden_fields` в профиле: скрытое не показывается работодателю и не участвует в оценке. Отзыв согласия —
  `DELETE /auth/me`, удаляет все связанные строки по схеме БД.
- Допы: `vacancies/` — вакансии и отклики (откликнуться может только кандидат с категорией, контакты
  раскрываются сразу); `challenges/` — регулярные задания, ответ обновляет актуальность профиля в ранжировании.
- Дизайн: применена дизайн-система «ФСП России» из Claude Design (проект 4bcf6a8c-e59a-48cd-812e-cc33caad7b5c,
  собрана по брендбуку). `frontend/src/styles/tokens.css` — токены без изменений, `theme.ts` — тема Mantine из
  них (синий #402FFF, красный #EC1D35, JetBrains Mono, радиусы 2/4/8), `styles/fsp.css` — правила, которых нет
  в теме. Цвета в компонентах задавать именами Mantine (`blue`, `red`, `gray`, `green`, `yellow`, `dark`) —
  палитры переопределены; других цветов в системе нет. Красный — не больше одного акцента на экран, капс —
  только класс `fsp-overline`, эмодзи не используются. Логотип не перекрашивать (`components/Logo.tsx`).
- Валидация (`backend/scripts/`): `synth.py` — синтетические кандидаты со скрытым уровнем, `validate.py`
  собирает отчёт `docs/validation_report.md`. Известные пределы, о которых надо говорить честно: один тест
  принимает верное решение по заявленному грейду в ~81% случаев, 23% кандидатов слабее заявленного проходят,
  надёжность балла 0,65, категория после всех попыток верна в ~75%; по доле подходящих в топе платформа
  уступает ранжированию «по резюме» при 20% завышающих грейд, почти равна при 35% и выигрывает при большей
  доле, зато кандидатов слабее запроса в топе всегда в 1,5–4 раза меньше. Мониторинг дрейфа при утечке
  200 тестов снижает долю проходящих списывающих с 83% до 46%, не до исходных 6%. Главный рычаг точности —
  размер банка.
- Потребность (`Need`) хранится, подборка считается при каждом открытии; уточняющие фильтры накладываются
  поверх и ни потребность, ни оценки не меняют. Словарь технологий — `reference/skills.py`.
- ФСП (`fsp/registry.py`): контракт `FspRegistry` (`fetch`, `rank`) + детерминированный мок (ID вида
  FSP-123456, кратные 7 не существуют, у части участников достижений нет). Копия достижений и разряд
  хранятся в профиле кандидата. Вес достижений (`fsp_strength`) — по числу и результату: победа 0,4,
  призовое место 0,3, участие 0,08 (все участия вместе не больше 0,2), старше двух лет ×0,6. Уровень
  соревнования и дисциплина на вес не влияют (позиция ФСП: все соревнования равно важны), разряд тоже.
- Схема БД создаётся через `create_all` при старте, миграций нет; при изменении моделей удалять `dev.db`.
- Инварианты под одновременными запросами держит база: частичные уникальные индексы (один незавершённый
  тест на кандидата, одно действующее приглашение на пару), версия строки у `Assessment` (один ответ на
  задание). В обработчиках `IntegrityError` / `StaleDataError` превращаются в 409.
- Входные схемы наследуются от `core/schemas.InputModel` (обрезка пробелов) и используют общие типы `Money`,
  `Tag`, `PathId`. Ошибки валидации переводит `core/errors.py`. Всё, что уходит работодателю о кандидате до
  согласия, проходит через `candidates/privacy.py` (скрытые поля, вырезание контактов из свободного текста).
- `SECRET_KEY` обязателен (значения по умолчанию нет): локально лежит в `.env` в корне, в тестах задаётся в
  `conftest.py`. Лимиты частоты (`core/ratelimit.py`) — в памяти процесса.
- Аудит от 06.10.2026 и регрессионные тесты по нему: `docs/qa-2026-10-06/REPORT.md`, `tests/test_qa_fixes.py`.
  Повторный аудит 07.10.2026 (`docs/qa-2026-10-07/REPORT.md`) нашёл один дефект — выход не отзывал JWT;
  тесты `test_qa2_*` там же.
- Срок пересдачи после провала (14 дней, этот грейд и выше) действует только в специализации проваленного
  теста (`assessment/router._grade_locks`, `AssessmentState.grades_by_specialization`); 90 дней на смену
  категории по-прежнему закрывают все специализации.
- Сессии: токен доступа несёт id сессии (`sid`), строка `AuthSession` (`auth_sessions`) проверяется на каждом
  запросе (`core/deps.find_session`), выход её удаляет. Токен без действующей сессии — 401. Сессию открывает
  только `auth/router.start_session`.
- Порты разработки: backend 8100, frontend 5183 (стандартные 8000 и 5173 на машине заняты).
- Тестирование кандидатов: банк параметризованных шаблонов заданий с заранее откалиброванной сложностью +
  адаптивный тест (IRT), лимит показов заданий. Валидация — симуляцией кандидатов с известным уровнем.
- Подбор: потребность работодателя → структура → категории → ранжирование по соответствию стеку и силе
  подтверждённого профиля (тест, достижения ФСП, свежесть) с объяснением «почему в подборке».
- ФСП: мок-реестр достижений; отсутствие истории ФСП — нейтральное состояние, без штрафа в ранжировании.

## Команды

- Тесты: `cd backend && .venv/Scripts/python -m pytest`
- Проверка фронтенда: `cd frontend && npm run build`
- Демо-данные: `cd backend && .venv/Scripts/python -m scripts.seed --reset` (удаляет все данные; входы и
  пароль — в описании `scripts/seed.py`). Демо-участники ФСП ID — `MockFspId.DEMO_ACCOUNTS`.
- Отчёт валидации: `cd backend && .venv/Scripts/python -m scripts.validate --out ../docs/validation_report.md`
  (около двух минут); статистика заданий по реальным попыткам — `python -m scripts.validate_testing --db`.
- Демо-сервер: после правок бэкенда перезапускать вручную (`--reload` на этой машине изменения не подхватил); база `dev.db` лежит в корне репозитория
  (uvicorn стартует оттуда), поэтому seed запускать из корня с `PYTHONPATH=backend`.
- Документация: править `docs/documentation.md`, затем `cd backend && .venv/Scripts/python -m scripts.build_docs` —
  соберёт `docs/documentation.pdf` (с разделом API из OpenAPI и отчётом валидации) и `docs/api.md`. Цифры
  валидации в разделе 6 документа вписаны вручную: после изменения движков сверять с отчётом.
- Запуск: конфигурации `backend` и `frontend` в `.claude/launch.json`.
